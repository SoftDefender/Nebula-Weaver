# Nebula-Weaver 项目逆向分析宪法（Analysis Constitution）

## 0. 适用范围
- [事实] 本宪法适用于 `E:\CodeProj\WebAIBox\Nebula-Weaver` 既有仓库的逆向分析、接手文档、迭代开发支持。
- [事实] 当前仓库为前端单仓库，且无额外 MCP/第三方分析平台接入；分析资源受上下文容量限制。
- [推断] 文档需长期复用，因此必须采用阶段化与证据索引策略。

## 1. 原则列表

### 原则1：事实优先，证据驱动，禁止臆测
- 原则：所有系统结论必须能回溯到代码、配置、脚本、运行结果。
- 原因：接手者需要可验证依据而非“解释性叙述”。
- 执行方式：每条关键结论标注 `[事实]/[推断]/[假设]/[待验证]`，并给文件+行号证据。
- 违例表现：出现“系统应该是这样”但无代码落点，或把 README 当作唯一真相。

### 原则2：模块级分析优先于文件级罗列
- 原则：先定义模块职责、边界、调用关系，再下钻函数/文件。
- 原因：文件清单不能支撑改需求与排障。
- 执行方式：每阶段先输出“模块地图 + 主链路 + 状态流”。
- 违例表现：只列目录和函数名，缺失跨模块行为解释。

### 原则3：先全景再细节
- 原则：分析顺序固定为：业务全景 -> 架构 -> 实现 -> 问题 -> 优化。
- 原因：避免在局部细节里迷失，导致结论失真。
- 执行方式：每份阶段文档都必须有“系统定位”和“边界”章节。
- 违例表现：先写实现细节却无法解释“系统为何存在”。

### 原则4：不确定项必须显式暴露
- 原则：证据不足时必须标记 `[NEEDS CLARIFICATION]` 或 `[待验证]`。
- 原因：隐藏不确定性会在接手期放大为误改风险。
- 执行方式：每阶段末尾固定“未确认事项列表”。
- 违例表现：用想当然补齐流程，后续代码无法自洽。

### 原则5：文档必须服务接手与改动
- 原则：所有产出面向“接手、定位、修改、扩展、排障”。
- 原因：交接文档的价值在于降低变更成本。
- 执行方式：每模块输出“入口、依赖、关键开关、易错点、排障抓手”。
- 违例表现：偏业务宣讲或 UI 介绍，缺少工程执行信息。

### 原则6：大仓库采用摘要继承机制
- 原则：每阶段都要产出“阶段摘要包 + 证据索引 + 精简继承上下文”。
- 原因：降低上下文爆炸风险，支持跨会话延续。
- 执行方式：正文后附紧凑包，保留最小但完整的继续分析输入。
- 违例表现：每轮重复全量叙述，信息冗余且不稳定。

### 原则7：优化建议必须受现实约束
- 原则：建议基于当前技术栈、团队能力、部署现状。
- 原因：脱离约束的“理想重构”不可执行。
- 执行方式：每条建议给出风险级别、前提条件、副作用。
- 违例表现：直接建议大重写，但无迁移路径。

### 原则8：明确区分三层结论
- 原则：文档必须拆分为“当前实现 / 理想设计 / 小步演进方案”。
- 原因：防止把愿景误写成现状。
- 执行方式：用矩阵或三栏对照输出。
- 违例表现：把未实现能力当成已交付能力。

### 原则9：文档长期维护优先
- 原则：用稳定结构和可检索编号管理文档资产。
- 原因：文档会成为后续需求与缺陷的工作基线。
- 执行方式：统一章节骨架、风险矩阵、证据索引格式。
- 违例表现：一次性报告风格，后续不可增量维护。

## 2. 文档证据等级说明
- `[事实]`：可由代码/配置/构建输出直接证明。
- `[推断]`：由多个事实归纳得出，源码未直接陈述。
- `[假设]`：当前证据不足但暂可用于工作推进的猜测。
- `[待验证]`：必须在后续阶段用新增证据闭环。

## 3. 分阶段分析约束
- 每次只覆盖一个阶段目标，不跨阶段扩写。
- 每阶段输出固定两部分：`A.完整分析正文` + `B.阶段摘要包（紧凑版）`。
- 优先分析：入口、主链路、核心模块、关键数据结构、重要配置。
- 输出必须附“下一阶段建议读取目标”。

## 4. 质量门禁（Quality Gates）
- QG-1：关键结论均有证据落点（文件/行号）。
- QG-2：不确定项全部显式标记，无隐式补全。
- QG-3：含可执行接手信息（启动、构建、配置、调试、排障）。
- QG-4：模块边界和主调用链能相互印证。
- QG-5：优化建议包含前提、风险、收益，不空泛。
- QG-6：摘要包可独立供下一阶段复用。

## 5. 阶段摘要包规范
- 必含字段：阶段目标、范围、关键事实、关键推断、风险点、未确认项、下一阶段输入。
- 体积要求：只保留高价值事实和关键链路，不重复正文细节。
- 证据要求：摘要中每个关键结论至少指向1条证据索引。

## 6. 最终交付件清单
- 项目概览与系统边界文档。
- 仓库切片与优先级路线图。
- 系统规格重建文档。
- 模块级深度逆向文档。
- 系统级流转文档（数据/控制/配置/错误/生命周期）。
- 风险与优化策略文档。
- 交叉一致性审计文档。
- 最终交接主文档（含术语表、证据索引、紧凑摘要）。

## 7. 后续阶段简版规则（<=10条）
1. 只写有证据的结论；缺证据就标 `[待验证]`。
2. 先讲模块职责和边界，再讲代码细节。
3. 每阶段必须产出“正文 + 紧凑摘要包”。
4. README 与代码冲突时，以代码为准并记录冲突。
5. 所有优化建议必须写清风险、前提和副作用。
6. 禁止把“想做的能力”写成“已实现能力”。
7. 重点维护主链路，不在非关键模块过度展开。
8. 每次结束给“下一阶段建议读取目标”。
9. 文档面向接手者，不写宣传性话术。
10. 优先保证可维护与可追溯，而非叙述完整感。
